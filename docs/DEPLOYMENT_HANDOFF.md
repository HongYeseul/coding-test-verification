## 배포 순서

마이그레이션을 `main` 배포보다 먼저 적용할지 나중에 할지는 **새 코드가 무엇을 부르느냐**로
갈립니다. SQL 파일 주석은 무엇을 왜 했는지까지만 적고 이 순서는 말하지 않습니다.

| 바꾸는 것 | 순서 | 어기면 |
|---|---|---|
| 함수 응답 모양·인자 | **먼저 적용** | 새 화면이 없는 인자로 호출해 깨집니다 |
| 컬럼·정책 추가 | 무관 | 구버전은 그 컬럼을 비워 둘 뿐입니다 |
| RPC 시그니처 교체 | 두 개를 잠시 공존 → 배포 후 옛것 제거 | 먼저 지우면 구버전 화면이 막힙니다 |

**앞으로 RPC 시그니처를 바꿀 때도 이 순서를 지킵니다.** 선례가 둘입니다 — `create_group`
2인자→3인자(`20260913010000`으로 옛것 제거), `list_group_directory()`→`get_group_directory()`
(`20260909030000`으로 옛것 제거). 인자 수가 다르면 두 정의가 공존해도 모호하지 않습니다.
인자 수가 같아지는 변경이면 한 트랜잭션으로 바꿔야 합니다.

CHECK 제약을 더할 때는 **적용 전에 위반 행이 없는지 먼저 봅니다.** 있으면 적용 자체가 실패합니다.
CHECK 안에서는 하위 질의를 못 쓰므로 판단이 필요하면 `IMMUTABLE` 함수로 뺍니다.

MCP의 `apply_migration`은 버전을 실행 시각으로 기록해 저장소 파일명과 어긋납니다. 적용한 뒤
`schema_migrations`의 해당 행을 파일명 버전으로 고쳐야 같은 파일이 다시 적용되지 않습니다.

## 리전

DB와 함수를 **함께** 서울로 옮겼습니다. 함수만 옮기면 그룹 화면의 순차 DB 대기가 전부 국제
왕복이 되어 오히려 느려집니다. 리전을 다시 만질 사람은 이 한 줄만 기억하면 됩니다.

측정은 절대값으로 비교하지 않습니다. 네트워크 상태가 매번 다르므로 **엣지 캐시 정적 자산을
기준선으로 두고 함수가 더하는 시간**을 봅니다. `x-vercel-id`가 `icn1::syd1` → `icn1::icn1`로
바뀌면서 그 값이 약 257ms에서 약 117ms가 됐습니다. 남은 117ms는 국제 왕복이 아니라 함수 렌더와
서울 안에서의 DB 왕복이라, 더 줄이려면 그룹 화면의 순차 대기를 손봐야 합니다.

## 되돌릴 때 볼 것

한 번 정한 뒤 잊기 쉬운데, 모르고 되돌리면 다시 깨지는 것들입니다.

- **멤버 정렬은 DB가 아니라 화면이 합니다.** 표시 규칙이라 바꿀 때마다 마이그레이션이 필요하지
  않도록 옮겼습니다. 응답에 `weekApproved`·`totalApproved`가 이미 있어 추가 조회가 없고, 전체
  멤버를 내려주므로 미리 정렬할 이유도 없습니다. **페이지네이션이 생기면 다시 DB로 옮겨야
  합니다.** 화면은 `localeCompare(…, "ko")`라 한글이 라틴 문자보다 앞에 옵니다 — DB의 `en_US`
  콜레이션과 반대이고, 이름 검색의 `toLocaleLowerCase("ko-KR")`와는 기준이 맞습니다.
- **`globals.css`의 기본 입력 규칙은 글자를 받는 입력에만 겁니다.** 체크박스·라디오·파일처럼
  스스로 모양을 가진 컨트롤을 빼지 않으면 너비 100%와 테두리가 씌워져 막대처럼 늘어납니다.
  새 입력 종류를 처음 쓸 때 걸리기 쉬우니, 화면을 볼 때는 반드시 앱의 스타일시트를 얹은
  상태로 보세요 — 토큰만 흉내 낸 미리보기로는 이 어긋남이 보이지 않습니다.
- **기본 엘리먼트 규칙은 반드시 `@layer base`에 둡니다.** 레이어 밖에 두면 명시도와 무관하게
  Tailwind 유틸리티를 항상 이겨 `w-36` 같은 지정이 먹지 않습니다. v4의 important는
  접미사(`w-36!`)이고 v3의 `!w-36`은 클래스가 아예 생성되지 않습니다.
- **디스코드 웹훅 주소는 앱이 읽지 않습니다.** `group_webhooks`는 RLS를 켜고 정책을 하나도 두지
  않아 아무도 직접 읽지 못하고, 보내는 일까지 DB 트리거가 `pg_net`으로 합니다. 설정 화면은
  `has_group_webhook()`으로 켜짐 여부만 압니다. **편하다고 주소를 돌려주는 함수를 만들지
  마세요** — 그 주소를 아는 사람은 누구나 그 채널에 글을 쓸 수 있습니다.
- **`set_group_webhook()`의 주소 검사를 느슨하게 풀지 않습니다.** `pg_net`은 어디로든 요청을
  보낼 수 있어서, 호스트를 디스코드로 못박지 않으면 DB가 내부망을 두드리는 도구가 됩니다.
- **웹훅 본문의 `allowed_mentions.parse`는 빈 배열로 둡니다.** 닉네임은 사용자가 정하는 값이라
  `@everyone`으로 바꿔 두면 서버 전체에 알림이 울립니다.
- **알림 문장은 DB가 만듭니다.** 화면 문구와 겹쳐 보여도 앱에서 글자를 받아 보내는 함수를 열면
  멤버 누구나 남을 사칭한 줄을 채널에 밀어 넣을 수 있습니다.
- **그룹 화면에는 `loading.tsx`를 두지 않습니다.** 주 이동 링크를 누를 때마다 깜빡입니다.
  대시보드와 프로필에는 있습니다.
- **`profiles`의 GitHub 아이디는 INSERT가 아니라 UPDATE 트리거로 채웁니다.** `auth.users` 삽입
  트리거가 만든 행이 identity보다 먼저 생기기 때문입니다.
- **RLS는 행 단위라 컬럼을 막지 못합니다.** `profiles`의 UPDATE 권한을 `display_name`·`bio`로
  좁혀 브라우저가 직접 요청해도 `github_login`이 바뀌지 않게 했습니다.
- **양방향 제어문자(U+202A~202E, U+2066~2069)는 앱에서 지웁니다.** 글자 순서를 뒤집어 사칭할 수
  있습니다. ZWJ는 이모지 결합 때문에 남깁니다.
- **문제 링크 검증은 두 겹입니다.** 브라우저가 `proofs`에 직접 INSERT할 수 있어서, DB CHECK는
  https와 길이만 보고 허용 호스트 판단은 앱이 저장할 때와 그릴 때 두 번 합니다. 호스트 목록을
  SQL에 두지 않아 플랫폼 추가에 마이그레이션이 필요 없습니다. 다만 **`extension/capture.js`에
  같은 목록이 한 벌 더 있으니** 둘을 같이 고쳐야 합니다.
- **`get_group_overview`가 돌려주는 `featuredProofId`·`featuredDate`는 화면에서 더 쓰지
  않지만 함수는 그대로 둡니다.**
- **함수를 고칠 때는 반드시 가장 최근 정의에서 시작하세요.** `get_group_overview`처럼 여러 번
  다시 정의된 함수는 옛 마이그레이션 파일에 낡은 본문이 그대로 남아 있습니다. 거기서 옮겨 오면
  그 사이에 들어간 수정이 조용히 되돌아갑니다. 2026-09-14에 실제로 두 개가 한꺼번에
  되돌아갔습니다 — 한국시간 새벽 3시 경계와 승인 집계의 자동 인정. 운영 DB의 현재 정의
  (`select prosrc from pg_proc …`)를 기준으로 삼는 편이 가장 안전합니다.
- **DELETE·UPDATE에는 SELECT 정책도 함께 걸립니다.** 지울 행을 찾을 때 읽기가 필요해서입니다.
  `proof_cheers`의 DELETE 정책에는 멤버십 조건이 없지만, 제명된 멤버는 SELECT 정책에 막혀
  자기 응원도 거두지 못합니다. 정책 하나만 보고 "이건 열려 있다"고 판단하면 어긋납니다.
- **BEFORE 트리거가 RLS의 WITH CHECK보다 먼저 걸립니다.** `private.validate_proof()`가 막는
  경우는 `42501`이 아니라 `P0001`로 돌아옵니다. `supabase/tests/*.sql`에서 거절을 확인할 때
  두 오류를 함께 받아야 합니다 — 한쪽만 잡으면 트리거가 먼저 막는 순간 테스트가 깨집니다.
- **멤버가 자기 `group_members` 행을 고칠 수 없습니다.** UPDATE 정책이 소유자 하나뿐입니다.
  목표(`goal_minutes`) 같은 자기 값을 열 때는 정책을 넓히거나 컬럼 권한을 새로 열지 말고
  `set_member_goal()`처럼 `security definer` 함수 하나로 좁히세요.

### 접근 범위

표 권한은 `ACTIVE` 멤버만 통과합니다. **예외는 `anon`에 열린 `security definer` 함수 둘뿐이고,
이 함수가 내보내는 값이 곧 비로그인에게 공개되는 전부입니다.**

- `get_group_directory()` — 그룹 이름과 인원수. 비공개 그룹도 목록에는 나옵니다
- `get_public_group_board(text)` — 공개로 연 그룹의 멤버 닉네임과 승인 건수

작성자 본인의 풀이 검수는 `proof_reviews` INSERT 정책이 막습니다.

### 남은 확인

- 디스코드 알림을 실제 웹훅으로 보내 본 적이 없습니다. 검증은 `net.http_request_queue`에 담긴
  본문까지만 봤고 디스코드가 그 본문을 받아 그리는 것은 확인하지 못했습니다. 그룹 설정에서
  주소를 넣고 도장을 한 번 찍어 채널에 줄이 올라오는지 봐야 합니다.
- 리전 이전 뒤 Real Experience Score를 다시 재지 않았습니다. 기준값(RES 62)은 대부분 이전 전에
  쌓인 값입니다.
- 상세 모달 동작을 운영 브라우저에서 확인하지 않았습니다. 로컬에서는 확인했습니다.
- 2026-09-14 개편 뒤 그룹 화면(오늘 띠·점선 도장·응원 버튼·기록 종류)을 브라우저에서 확인하지
  못했습니다. 로그인이 필요한 화면인데다, **회사 프록시의 self-signed 인증서 때문에 로컬 Node가
  Supabase에 붙지 못합니다**(`SELF_SIGNED_CERT_IN_CHAIN`). curl은 시스템 CA를 써서 되고 Node만
  막히므로, 로컬에서 데이터가 있는 화면을 보려면 프록시 인증서를 `NODE_EXTRA_CA_CERTS`로
  물려야 합니다. 첫 화면과 공개 리더보드는 운영 응답으로 확인했습니다.
- 기상·착석 스터디의 화면은 실제 데이터로 본 적이 없습니다. 그룹 설정에서 기록 종류를 켠 뒤
  도장판 칸·목표 다이얼로그·내 리듬 차트·착석 시간 차트를 한 번 훑어야 합니다. 특히 착석은
  착석 도장 → 퇴근 도장 두 단계를 실제로 눌러 봐야 합니다.
- `supabase/tests/group_overview.sql`은 아직 `(now() at time zone 'Asia/Seoul')::date`로
  오늘을 구합니다. 함수는 새벽 3시 경계를 쓰므로 이 테스트는 00시~03시 사이에 실행하면
  실패합니다. 그 시간대에 돌릴 일이 있으면 먼저 고쳐야 합니다.
